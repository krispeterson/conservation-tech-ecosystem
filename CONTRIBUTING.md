# Contributing

Thanks for improving this list.

## What belongs here

Additions are most useful when they are:

- operationally relevant
- maintained by a credible organization, lab, NGO, company, or community
- documented well enough for others to discover and use
- clearly connected to conservation, restoration, biodiversity monitoring, protected area operations, fisheries transparency, marine monitoring, or related environmental workflows
- strategically useful as a platform, standard, device ecosystem, repository, or collaboration layer

## What usually does not belong here

Please avoid adding:

- abandoned student projects
- generic AI or GIS tools with no real conservation connection
- one-off scripts with no documentation
- marketing pages with no evidence of product, community, or ecosystem relevance
- duplicate entries under slightly different names

## Preferred structure for additions

For tools and platforms, try to include:

- name
- short one-line description
- open-source, proprietary, hybrid, or community-led status if known
- why it matters or what workflow it supports
- official link

For repositories, include:

- repository or organization name
- why it matters
- what makes it useful to others
- whether it is foundational, promising, or niche

For standards and interoperability layers, include:

- official name
- what problem it solves
- where it is used in practice
- links to specification or maintainer page

## Curation standard

This repo is intentionally selective.

The bar is not “largest project wins.” The bar is “useful enough that someone serious in the field would benefit from knowing about it.”

## Good pull requests

Strong pull requests tend to do one of these:

- tighten taxonomy
- improve domain coverage
- add missing standards or schemas
- add credible open-source repos that are easy to miss
- improve descriptions so the repo is more decision-useful
- remove stale or misleading entries


## Especially useful contributions

High-value pull requests include:

- integration patterns that show how data moves between field tools, analysis systems, operational platforms, and archives
- concrete notes on export formats, schemas, and APIs used in real deployments
- examples of offline-first or low-bandwidth workflows that work in practice
